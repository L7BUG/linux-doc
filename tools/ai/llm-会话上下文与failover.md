# LLM 会话上下文与故障转移原理

> **背景**：在 cc-switch 路由模式下，当主模型供应商因熔断触发故障转移（failover）时，对话上下文是否会丢失？长对话为什么越来越慢？本文从原理层面解释这些问题的答案。

---

## 1. LLM 是无状态的

这是理解一切的前提。API 本身**不记得**上一轮说了什么——每次请求，客户端必须把**整个对话历史**（所有 `user` 和 `assistant` 消息）重新发给 API，模型才能"知道"之前聊了什么。

```
请求 #1: [user: "你好"]

请求 #2: [user: "你好", assistant: "你好！有事吗？", user: "帮我写个函数"]

请求 #3: [user: "你好", assistant: "你好！有事吗？", user: "帮我写个函数",
         assistant: "好的，这是代码...", user: "再加个注释"]
```

每轮的请求体都比上一轮大，累积的是**全部历史消息**。

## 2. 故障转移时上下文为什么不会丢

### 2.1 上下文的位置

```
┌─────────────────────────────────────────────────────┐
│ Claude Code / Codex CLI（本地客户端）                │
│ ┌─────────────────────────────────────────────────┐ │
│ │ 对话历史（所有 user + assistant 消息）            │ │
│ │ ↓ 每次请求一起发出                               │ │
│ └─────────────────────────────────────────────────┘ │
│            │                                         │
│            ▼                                         │
│  cc-switch（本地代理 :15721）                        │
│  ┌──────────────┐    ┌──────────────┐               │
│  │ 供应商 A      │    │ 供应商 B      │               │
│  │ (主)          │───▶│ (备用, failover)│             │
│  └──────────────┘    └──────────────┘               │
└─────────────────────────────────────────────────────┘
```

关键点：

- **上下文不在 cc-switch 手里**——它只是个透明代理，不存储对话
- **上下文不在 API 供应商手里**——API 是无状态的，请求结束就忘了
- **上下文在 Claude Code（客户端）本地维护**

### 2.2 Failover 流程

```
对话进行中 (供应商 A)
        │
        ├── 供应商 A 返回错误 / 超时 / 不可用
        │
        ▼
cc-switch 熔断触发
        │
        ├── 标记供应商 A 为不健康
        ├── 切换到供应商 B
        │
        ▼
Claude Code 继续发送请求
    请求体 = 完整对话历史（和之前完全一样）
        │
        ▼
供应商 B 收到完整上下文
        │
        ├── 看到整个对话历史
        ├── 像什么都没发生一样继续回答
```

**结论**：切换在 Claude Code 看来是无感知的——它只是把同样的请求发到了另一个地址，上下文毫发无损。

### 2.3 什么会丢失：Prompt Cache

| 项目 | Failover 后 | 说明 |
|------|------------|------|
| 对话文本 | ✅ 完整保留 | 客户端本地持有，每次请求都带着 |
| 历史消息 | ✅ 完整保留 | 同上 |
| Prompt Cache | ❌ 全部失效 | 不同供应商的缓存系统独立，A 的缓存对 B 毫无意义 |
| Token 费用 | ⚠️ 短期上升 | 切换后首轮无缓存命中，按全价计费 |

> **提示**：Prompt Cache 的原理是供应商识别请求前缀是否与之前某次请求相同。换供应商意味着前缀对比的基准完全变了，缓存自然无法命中。不过继续使用供应商 B 几轮后，缓存会重新建立起来。

## 3. 长对话为什么越来越慢

### 3.1 根本原因：Transformer 的注意力机制

LLM 底层是 Transformer 架构，其自注意力机制的计算复杂度是 **O(n²)**——上下文翻倍，计算量大约是原来的 **4 倍**。

```
上下文长度    相对计算量
──────────────────────────
  10K tokens  ████
  50K tokens  ████████████████████
 100K tokens  ████████████████████████████████████████
 200K tokens  ██████████████████████████████████████████████████████████████████████████████████████████████████████████████████████████████████████████████████
```

这和"每次请求都带完整历史"的设计叠加在一起，意味着**每轮请求都比上一轮更慢**。

### 3.2 Claude Code 的缓解策略

#### 自动压缩（Compaction）

当上下文接近窗口上限时，Claude Code 自动触发压缩——把早期对话提炼为一段摘要，替换掉原始消息：

```
压缩前: [50 轮详细对话, ~300K tokens]
                          ↓
压缩后: [摘要: "用户之前讨论了 X 项目的架构...",
         最近 5 轮完整保留, ~80K tokens]
```

> **注意**：压缩后极早期的细节可能被摘要替代，如果你需要引用很早之前的内容，可能不会被完整保留。

#### Prompt Caching（同一供应商内）

Anthropic API 对请求前缀进行缓存。如果前缀不变（早期历史未被修改），这些 tokens 的处理会显著加速且费用更低（cache write 价格高于 base，但 cache read 价格远低于 base）。

仅在**同一供应商内**有效，换供应商即失效。

#### 上下文窗口参数

Claude Code 内部有最大上下文 token 限制，防止无限制膨胀。cc-switch 会为不同模型注入合适的窗口参数：

| 场景 | 窗口参数 |
|------|---------|
| Claude Opus 1M（直连） | 由 Claude Code 自动启用 |
| GPT-5.6（Codex + cc-switch） | cc-switch 注入 372K 窗口 |
| Kimi For Coding（Codex + cc-switch） | cc-switch 注入 256K 窗口 |

### 3.3 各阶段的体感表现

| 阶段 | 上下文量 | 响应速度 | 说明 |
|------|---------|---------|------|
| 新会话（前 30 轮） | 小 | 🟢 很快 | O(n²) 常数还小，几乎无感 |
| 中等长度（30–100 轮） | 中等 | 🟡 略有延迟 | 可接受，大约多等 1-2 秒 |
| 长对话（100+ 轮） | 大 | 🟠 明显变慢 | 可能接近窗口上限 |
| Compaction 之后 | 小（摘要+最近） | 🟢 恢复流畅 | 早期细节被摘要替代 |
| Failover 切换后 | 不变 | 🟡 缓存命中率下降 | 上下文完整，但首轮按全价计费 |

## 5. 实践建议

### 5.1 会话管理

- **一个任务一个会话**：不要在一个会话里堆积多个不相关的任务，任务完成后开启新会话
- **关注 compaction 提示**：当 Claude Code 提示正在压缩上下文时，说明当前会话已经很长，建议尽快收尾
- **长任务中途 `/clear`**：如果感觉响应明显变慢，主动清空上下文，简要交代当前进展后继续

### 5.2 供应商切换

- **手动切换**：不用担心丢失上下文，切换后继续对话即可。首轮可能稍慢（无缓存），后续恢复正常
- **故障转移**：完全自动，无需人工干预。供应商恢复后 cc-switch 会自动切回
- **缓存成本意识**：频繁切换供应商会导致缓存频繁重建，增加费用。如果对成本敏感，尽量保持稳定的供应商选择

### 5.3 路由模式下注意事项

- **不要加 `[1m]` 后缀**：路由模式下，provider 模型名应使用规范名称（如 `deepseek-v4-pro`），`[1m]` 后缀仅在直连时使用
- **保持 provider 名称一致**：对 Codex 等工具，切换供应商时确保 `config.toml` 中 provider 名称统一，避免会话"丢失"的假象

## 6. 常见问题

### Q: 切换供应商后，我之前的对话还在吗？

**在。** 对话历史存储在 Claude Code 本地，切换供应商只是改变了请求发往的目的地，不影响本地的任何数据。

### Q: 为什么切换后第一轮回复看起来很贵？

因为之前的 prompt cache 无法命中，首轮请求按全价计费。继续使用同一供应商几轮后，缓存会重新建立，费用恢复正常。

### Q: Compaction 后我会丢失什么？

早期对话的**详细内容**会被浓缩为摘要。如果你之前让 Claude 记住了某个具体偏好或细节，且该信息在早期的某轮对话中，压缩后可能只会以概要形式保留。关键的约定或偏好建议在压缩后主动重申。

### Q: 长对话有没有办法不压缩也保持较快速度？

基本没有。O(n²) 是 Transformer 的固有数学特性，不是工程优化能绕过的。唯一的办法就是控制上下文长度——要么压缩，要么开新会话。

### Q: cc-switch 的熔断是多久检测一次？

每个 CLI 应用（Claude Code、Codex、Gemini）有独立的故障转移队列，健康检查在请求失败时即时触发，非定时轮询方式。
